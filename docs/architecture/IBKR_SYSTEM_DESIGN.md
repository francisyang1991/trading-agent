

# IBKR API 美股股票+期货程序化交易系统设计报告

## 1. 系统架构与连接层设计

### 1.1 网关选型与部署策略

#### 1.1.1 TWS vs IB Gateway 生产环境对比

在构建生产级IBKR API交易系统时，**网关选型是首要架构决策**。Interactive Brokers提供两种核心接入方式：Trader Workstation (TWS) 和 IB Gateway，二者在API功能层面完全等价，但资源特性和运维模式存在显著差异 [^292^]。

**IB Gateway的核心优势在于其轻量级无GUI架构**。实测数据显示，Gateway的内存占用比TWS低约40%（典型配置512MB-1GB vs 2-4GB），启动时间从30-45秒压缩至10-15秒 [^292^]。这一特性对于需要7×24小时稳定运行的中低频交易系统至关重要——更低的资源消耗意味着在同一硬件配置上可并行运行更多策略实例，或为风险计算和数据处理预留更多headroom。此外，Gateway去除图形界面组件后，潜在故障点减少，长期运行稳定性优于TWS。

然而，**Gateway的调试劣势不容忽视**。缺乏可视化界面意味着所有状态诊断依赖日志输出和API查询，订单状态追踪、持仓核对、连接健康度监控等操作的复杂度显著上升。TWS提供的Risk Navigator、实时订单簿、账户摘要等工具，在开发阶段能够快速定位合约配置错误、订单异常等常见问题。因此，**推荐采用"开发-TWS、生产-Gateway"的双轨模式**：策略开发和调试阶段使用TWS验证逻辑，生产部署迁移至Gateway优化资源效率 [^278^]。

**单连接架构下的并发处理**是混合资产策略的关键设计挑战。IBKR API采用TCP长连接协议，单个`clientId`对应一条独立连接通道，所有市场数据订阅、订单操作、账户查询共享该连接。ib_insync框架通过单一asyncio事件循环管理这些异步操作，将底层回调机制转换为直观的协程接口。对于股票+期货混合策略，需实现**优先级分层调度**：交易指令（尤其是风控平仓）享有最高优先级，实时数据订阅次之，历史数据下载和日志写入等后台任务优先级最低。这种设计在接近50 msg/s的速率限制下，确保关键操作的及时执行 [^365^]。

**本地服务器同机部署**是降低系统延迟的核心措施。将核心交易逻辑与TWS/Gateway部署于同一物理机器，网络往返时间（RTT）可从跨机部署的毫秒级压缩至亚毫秒级（<0.1ms）。对于中低频策略，这一优化在常规时段影响有限，但在市场剧烈波动期间——当交易所订单簿深度快速变化时——即使是数十毫秒的延迟差异也可能导致滑点显著增加。更重要的是，同机部署消除了对外部网络的依赖，降低了网络分区导致的连接中断风险 [^322^]。

| 维度 | TWS | IB Gateway | 生产建议 |
|:---|:---|:---|:---|
| 内存占用 | 2-4GB | 512MB-1GB | **Gateway优先** |
| 启动时间 | 30-45秒 | 10-15秒 | **Gateway优先** |
| 图形界面 | 完整 | 无 | 开发用TWS，生产用Gateway |
| API功能完整性 | 100% | 100% | 等价 |
| 调试便利性 | 高 | 低 | 需配套日志系统 |
| 长期稳定性 | 中等 | **高** | **Gateway优先** |
| 自动更新干扰 | 有 | 无 | Gateway更可控 |

#### 1.1.2 自动化启动与认证管理

生产环境的**无人值守运行要求解决IBKR的定期认证痛点**。根据官方机制，会话token固定7天失效，且客户端IP地址变更会立即终止会话 [^300^]。这一安全设计对自动化交易系统构成显著稳定性挑战——必须中断交易流程进行人工干预。

**IBC（Interactive Brokers Controller）工具**是实现自动登录的主流开源方案。IBC通过拦截和模拟TWS/Gateway的Java UI事件，自动完成凭证填充和登录流程。其核心配置包括：加密存储的用户名密码、交易模式指定（live/paper）、以及定时重启调度 [^307^][^311^]。关键配置片段示例：

```
[IBGateway]
TWSPath=/opt/ibgateway
TWSMajorVersion=1035
IbLoginId=your_username
IbPassword=your_password
TradingMode=live
SecondFactorAuthentication=manual
RestartTime=07:00
```

**子账户模式是更优雅的认证绕过方案**。主账户保留完整的双重认证（2FA）保护用于资金存取等敏感操作，创建专用API交易子账户并配置为"仅API访问"模式，可禁用2FA或设置为信任设备自动认证 [^300^][^361^]。这种架构的安全优势在于：主账户的高安全性不受影响，子账户的权限隔离降低单点泄露风险，同时实现API连接的完全自动化。需要注意的是，子账户需要独立的市场数据订阅，增加了固定成本。

**自动重启机制**的稳定性随版本演进显著改善。TWS 974+版本引入受控重启功能，可从周日持续运行至次周周日，仅在周六晚间服务器重置后需要重新认证 [^292^][^312^]。推荐配置每日凌晨（如07:00 ET）的自动重启窗口，避开交易时段的同时完成内存清理和合约定义更新。结合子账户的免2FA配置，可实现**周级别的高可用运行**。

### 1.2 ib_insync 异步框架深度应用

#### 1.2.1 事件循环与混合流处理

**ib_insync的核心设计哲学是将底层异步回调模式转换为直观的同步风格代码**。框架基于Python asyncio构建单一事件循环，所有与TWS/Gateway的通信——市场数据订阅、订单提交、账户查询——都通过该循环调度。这种抽象对于股票+期货混合策略尤为关键：开发者无需处理复杂的回调注册和状态同步，能够以接近同步代码的风格编写高性能异步逻辑 [^283^][^295^]。

**异步上下文管理器确保连接生命周期的优雅管理**。典型的连接模式：

```python
from ib_insync import IB, Stock, Future

async def trading_session():
    async with IB() as ib:
        await ib.connect('127.0.0.1', 4002, clientId=1)
        
        # 股票与期货合约并发验证
        aapl = Stock('AAPL', 'SMART', 'USD')
        es = Future('ES', '202503', 'GLOBEX')
        await ib.qualifyContractsAsync(aapl, es)
        
        # 统一数据订阅
        ib.reqMktData(aapl, '', False, False)
        ib.reqMktData(es, '', False, False)
        
        # 事件驱动主循环
        ib.pendingTickersEvent += on_tick_update
        await ib.run()
    # 自动断开连接，清理资源
```

**回调与轮询的混合使用**是处理不同数据类型的有效策略。实时市场数据（`reqMktData`）和订单状态更新（`filledEvent`/`statusEvent`）采用回调模式实现事件驱动响应；账户摘要（`accountValues`）和持仓数据（`positions`）等相对静态信息，采用定时轮询（如每30秒）降低复杂度。这种混合架构在保持响应性的同时，避免了纯回调模式的代码分散问题。

#### 1.2.2 连接状态机设计

**生产级系统需要精确定义连接的生命周期状态**。推荐的三态扩展模型：

| 状态 | 定义 | 进入条件 | 退出条件 | 处理策略 |
|:---|:---|:---|:---|:---|
| **CONNECTED** | 连接正常，可交易 | `isConnected()==True`且收到有效ID | 检测到连接异常 | 正常运行 |
| **DEGRADED** | 连接存活但功能受限 | 部分请求超时、特定错误代码 | 恢复正常或恶化 | 降级运行，暂停非关键操作 |
| **DISCONNECTED** | 完全断开 | `isConnected()==False` | 启动重连流程 | 标记状态，触发重连 |
| **RECONNECTING** | 重连进行中 | 进入DISCONNECTED后自动触发 | 重连成功或达到最大重试 | 指数退避，状态同步 |
| **FATAL** | 致命错误，需人工介入 | 认证失败、账户冻结等 | 人工修复后重置 | 告警通知，系统锁定 |

**连接异常的分类处理**是状态机的核心逻辑。网络层故障（TCP重置、超时）具有瞬时性，采用**指数退避重连**：首次间隔1秒，后续翻倍至最大60秒，成功后重置计数器 [^332^]。API服务层故障（如2106"HMDS连接中断"）通常与特定服务相关，系统应降级为仅交易模式，暂停历史数据请求。致命错误（如502"客户端ID过多"）需立即告警，等待人工介入。

**重连成功后的状态同步**不可或缺：重新订阅市场数据流、查询未结订单状态（`reqOpenOrders`）、核对持仓一致性（`positions` vs 本地缓存）。任何不一致触发告警，必要时暂停交易等待人工确认。

#### 1.2.3 错误代码映射与处理

IBKR API的错误代码体系是系统健康监控的关键信号源。建立**分层错误处理策略**，将错误映射为可恢复或致命类型：

| 代码系列 | 典型代码 | 含义 | 处理策略 |
|:---|:---|:---|:---|
| 2100-2199 | 2104, 2106, 2107 | 市场数据/HMDS连接状态 | 监控日志，标记数据质量 |
| 1100-1199 | 1100, 1101, 1102 | TWS连接中断/恢复 | 状态机转换，触发重连/同步 |
| 500-599 | 502, 504 | 连接拒绝/超时 | 检查配置，指数退避重试 |
| 200-299 | 200, 321 | 合约无效/需验证 | 合约参数修正，人工复核 |
| 300-399 | 399 | 订单被拒绝 | 解析原因，决策重试或告警 |

**自定义异常层级**提升代码可维护性：

```python
class IBKRError(Exception): pass
class RecoverableError(IBKRError):  # 网络抖动、临时限频
    def __init__(self, code, msg, retry_after=60):
        self.retry_after = retry_after
        super().__init__(msg)
class FatalError(IBKRError):  # 需人工介入
    def __init__(self, code, msg, action):
        self.action = action
        super().__init__(msg)
```

### 1.3 限频控制与性能优化

#### 1.3.1 消息速率管理

**50 msg/s是IBKR API的硬约束**，超限将导致临时封禁（数分钟至数小时）[^365^]。该限制涵盖所有消息类型（请求+响应），生产系统必须实现主动流量控制。

**令牌桶算法**实现平滑流量控制：

```python
class RateLimiter:
    def __init__(self, rate=50, capacity=50):
        self.rate = rate          # 令牌补充速率（个/秒）
        self.capacity = capacity  # 桶容量（突发容忍）
        self.tokens = capacity
        self.last_update = time.monotonic()
        self.queues = {
            'critical': asyncio.PriorityQueue(),  # 交易指令
            'data': asyncio.PriorityQueue(),       # 实时数据
            'background': asyncio.PriorityQueue(), # 历史数据、日志
        }
    
    async def acquire(self, priority='data', cost=1):
        # 等待令牌可用，按优先级排队
        ...
```

**请求队列的三级优先级**确保关键操作优先：P0（紧急平仓、风控订单）立即执行；P1（常规交易、实时数据）正常调度；P2（历史下载、报表生成）后台节流。股票与期货数据请求虽属同级，但期货主力合约（ES/NQ）的更新频率更高，在资源竞争时赋予加权优先级。

#### 1.3.2 历史数据批量下载优化

**分段并行请求**突破单请求数据量限制。将长周期需求拆分为多个短周期请求（如1年数据拆为12个月度请求），在令牌桶许可范围内并行执行。关键控制参数：最大并发度（建议5，避免触发限频）、请求间隔动态调整（成功时缩短至100ms，检测到压力时延长至500ms）、以及失败重试的指数退避。

**股票与期货请求的优先级分离**基于业务特性。期货数据（尤其是CTA策略依赖的ES/NQ）的时效性要求更高，在队列调度中优先保障；股票基本面数据（如财务指标）更新频率低，可充分节流。历史数据下载建议集中在交易清淡时段（如美股收盘后、亚洲时段）执行，释放带宽给实时交易。

## 2. 统一合约管理与数据接入层

### 2.1 Contract对象设计与实现

#### 2.1.1 股票合约配置

股票合约的配置相对标准化，**核心在于Smart路由的自动优化**。Smart路由实时比较各交易所的流动性、费用和延迟，选择最佳执行路径。对于流动性充足的美股大盘股，这一机制通常无需人工干预；但对于小盘股或特定时段，可通过`primaryExchange`参数强制指定主交易所。

必需字段简洁明确：
- `symbol`: 股票代码（注意BRK.B等特殊格式需写作"BRK B"）
- `secType`: 'STK'（股票）
- `exchange`: 'SMART'（智能路由）
- `currency`: 'USD'

`qualifyContracts`方法自动补全`conId`等字段，验证后的合约对象应缓存复用，避免重复查询消耗速率配额。

#### 2.1.2 期货合约精确配置

期货合约的配置复杂度显著高于股票，**核心挑战在于交易所指定、合约规格精确性和到期月份管理**。任何字段偏差都可能导致"无安全定义"错误（Error 200），这是IBKR开发中最常见的陷阱之一 [^278^]。

**核心品种规格必须精确掌握**：

| 品种 | 标的 | 交易所 | 乘数 | 最小变动 | 每tick价值 | 典型流动性 |
|:---|:---|:---|---:|---:|---:|:---|
| **ES** | 标普500指数 | GLOBEX | $50 | 0.25点 | **$12.50** | 极高，日成交>200万手 |
| **NQ** | 纳斯达克100指数 | GLOBEX | $20 | 0.25点 | **$5.00** | 极高，日成交>100万手 |
| **YM** | 道琼斯工业指数 | GLOBEX | $5 | 1点 | **$5.00** | 高，略低于ES/NQ |
| **CL** | WTI原油期货 | NYMEX | 1,000桶 | $0.01/桶 | **$10.00** | 极高，全球基准 |
| **GC** | 黄金期货 | COMEX/NYMEX | 100盎司 | $0.10/盎司 | **$10.00** | 极高，避险资产 |

**localSymbol优先策略**是避免到期月份歧义的最佳实践。`localSymbol`（如'ESH5'表示2025年3月到期的ES期货）是交易所分配的唯一代码，直接指定可绕过`lastTradeDateOrContractMonth`的解析逻辑。月份代码规则：F(1月)、G(2月)、H(3月)、J(4月)、K(5月)、M(6月)、N(7月)、Q(8月)、U(9月)、V(10月)、X(11月)、Z(12月)。

```python
# 推荐：localSymbol精确指定
es = Future(localSymbol='ESH5', exchange='GLOBEX')

# 备选：symbol+到期月（需验证）
es = Future('ES', '202503', 'GLOBEX')
```

#### 2.1.3 合约验证与解析

**`reqContractDetails`**返回合约的完整元数据，包括交易时间、最小变动、价格放大因子、到期日等。**`qualifyContracts`**是ib_insync的高级封装，自动补全缺失字段并验证有效性 [^284^]。

**ConId缓存机制**优化重复查询性能。`conId`是IBKR内部永久标识符，验证后持久化至本地映射表（SQLite/JSON），后续直接使用`Contract(conId=xxx)`重建对象，绕过网络延迟。缓存条目包含验证时间戳，定期（每周）刷新以应对合约到期和新上市。

### 2.2 期货换月(Roll Over)自动化

#### 2.2.1 主力合约检测逻辑

期货合约的有限生命周期要求**自动换月机制**。主力合约判定采用**成交量与持仓量双指标加权**：

```
主力得分 = 0.6 × 成交量排名 + 0.4 × 持仓量排名
```

**换月提前期**因品种而异：指数期货（ES/NQ/YM）流动性切换快，建议到期前5-8个交易日；商品期货（CL/GC）交割规则复杂，建议8-12个交易日。触发条件包括：次月合约成交量>旧合约×1.5倍、旧合约买卖价差>3×正常水平、或强制到期前2日。

**连续合约构建**采用**向后调整法**（backward adjustment）：换月时记录新旧合约价差，将历史价格序列平移该价差，消除跳空保持收益率连续性。调整因子持久化存储，支持多版本连续合约（基于成交量/持仓量换月）的敏感性分析。

#### 2.2.2 换月执行策略

**"先开后平"顺序**降低敞口风险：先开仓新合约建立目标敞口，确认成交后再平仓旧合约。这一顺序避免了中间状态的净敞口暴露。

**滑点控制**要求避开高波动时段：开盘首15分钟、收盘前15分钟、以及重要经济数据发布前后30分钟。换月期间价差波动加剧，限价单替代市价单，设置合理滑点容忍度（ES推荐2-4 ticks，$5-10）。

### 2.3 实时数据流架构

#### 2.3.1 Level 1市场数据

**`reqMktData`**订阅Level 1数据（Bid/Ask/Last/Volume），ib_insync提供统一处理接口。股票与期货的`Ticker`对象自动更新，通过`ib.ticker(contract)`获取引用。

**实时Bar构建**支持多时间框架：
- **5秒Bar**：`reqRealTimeBars`直接订阅，CPU效率最优
- **1分钟/5分钟Bar**：基于5秒Bar二次聚合，或`reqHistoricalData`的`keepUpToDate=True`模式
- **日级Bar**：交易时段结束聚合

Bar构建器需处理时间戳对齐（交易所官方时间）、缺失值填充（前向填充）、以及盘后/盘前数据筛选（`useRTH`参数）。

#### 2.3.2 Level 2深度数据评估

**DOM数据的必要性需严格评估**。Level 2提供订单簿多档报价，对于高频策略（做市、订单流分析）不可或缺，但中低频策略的成本效益比通常不佳：

| 数据类型 | 月费用 | 适用场景 | 中低频策略建议 |
|:---|:---|:---|:---|
| Level 1 (Basic) | $0-10 | 常规交易 | **必需，基础配置** |
| Level 2 (CME) | $100-200 | 高频、大单执行优化 | 通常非必需 |
| 时间销售数据 | $20-50 | 逐笔分析 | 可选 |

**替代方案**：Level 1数据结合成交量分布分析，可近似推断支撑阻力位和订单簿压力，实现成本效益更优的流动性评估。

### 2.4 历史数据管理

#### 2.4.1 存储方案选型

| 方案 | 适用场景 | 优势 | 劣势 | 本系统建议 |
|:---|:---|:---|:---|:---|
| **SQLite** | 单策略、<100GB | 零配置、单文件、Python原生 | 并发写入瓶颈、无内置时序函数 | **初期首选** |
| **InfluxDB** | 多策略、高频数据、扩展需求 | 高吞吐、连续查询、自动降采样 | 运维复杂度、学习曲线 | 规模增长后迁移 |
| **Parquet+分区** | 大规模分析、云原生 | 压缩率高、列式存储、生态丰富 | 实时写入弱 | 冷数据归档 |

**SQLite推荐配置**：WAL模式（`PRAGMA journal_mode=WAL`）提升并发，`PRAGMA synchronous=NORMAL`平衡安全与性能，分表存储不同品种和频率。

#### 2.4.2 数据一致性处理

**股票复权调整**：前复权（调整历史价格）适用于信号生成，后复权（调整当前价格）适用于P&L核算。IBKR的`whatToShow='ADJUSTED_LAST'`提供调整后数据，但建议自行维护复权因子表以确保可追溯性。

**期货连续合约**：同时存储原始合约价格和连续合约价格，前者用于实际交易执行，后者用于信号生成和绩效分析。换月调整量单独记录，支持多版本比较。

**跨品种时间戳对齐**：统一转换为UTC或America/New_York时区，处理夏令时变更。缺失值采用前向填充，标记填充区间避免虚假信号。

## 3. 订单执行与算法交易引擎

### 3.1 订单类型矩阵与场景适配

| 交易场景 | 订单类型 | 核心参数 | 适用标的 | 执行特性 | 风险控制 |
|:---|:---|:---|:---|:---|:---|
| **紧急平仓/风控** | **MKT** | 无 | 股票、期货 | 立即成交，价格不确定 | 仅用于P0级风控 |
| 股票市价入场 | MKT | 无 | 股票 | 快速执行，接受滑点 | 流动性充足时使用 |
| 股票限价入场 | **LMT** | `limitPrice`, `tif='GTC'/'DAY'` | 股票 | 价格控制，可能不成交 | 非紧急场景首选 |
| 期货突破追单 | **STP** | `stopPrice`, `triggerMethod='LAST'` | 期货 | 触发后转市价 | 趋势跟踪入场 |
| 期货趋势跟踪 | **STP LMT** | `stopPrice` + `limitPriceOffset` | 期货 | 触发后转限价，控制滑点 | 高波动品种推荐 |
| 收盘调仓 | **MOC** | 无 | **仅股票** | 16:00 ET集合竞价 | 截止时间前提交 |
| 期货夜盘限价 | LMT | `limitPrice`, `outsideRth=True` | 期货 | 几乎24小时交易 | 注意流动性时段差异 |

**STP LMT的限价区间设置**是关键权衡。ES期货推荐`limitPriceOffset=2-4 ticks`（$5-10），过小可能无法成交，过大失去保护意义。CL/GC等波动剧烈品种可适当放宽。

### 3.2 IB智能算法(Algos)集成

#### 3.2.1 股票大单执行：Adaptive Algo

**Adaptive Algo动态调整执行激进程度**，`urgency`参数（1-10）控制速度vs冲击权衡：

| Urgency | 适用场景 | 预期效果 |
|:---|:---|:---|
| 1-3 | 大额建仓，冲击敏感 | 低冲击，长执行时间，价格改善概率高 |
| 4-6 | 常规执行，平衡需求 | 中等速度，适度价格改善 |
| 7-10 | 紧急平仓，流动性优先 | 快速完成，接受一定冲击 |

对于$50K-500K账户规模，单笔股票订单通常<$50K，**urgency=5-7是合理起点**。可通过A/B测试比较实际执行价格与VWAP偏离度优化参数。

#### 3.2.2 期货算法执行：VWAP/TWAP

| 算法 | 核心机制 | 适用场景 | 关键参数 |
|:---|:---|:---|:---|
| **VWAP** | 按预测成交量分布拆分 | 流动性模式稳定、绩效基准为VWAP | 时间窗、最大参与率(10-30%)、紧急程度 |
| **TWAP** | 按时间均匀拆分 | 流动性不确定、需平稳执行 | 时间窗、子单数量、允许超时 |

期货算法的**时间窗配置**需避开流动性枯竭时段：ES/NQ的亚洲时段（20:00-02:00 ET）价差扩大，建议将主要执行窗口限制在欧美重叠时段（08:00-16:00 ET）。

### 3.3 订单生命周期管理

#### 3.3.1 状态转换追踪

IBKR订单状态机的完整流程：

```
PendingSubmit → PreSubmitted → Submitted → {Filled, Partial, Cancelled, Inactive}
     ↑              ↑              ↑
   本地发送      交易所预检      交易所接受
```

**双模式回调处理**：`filledEvent`（每次成交触发，含价格/数量/时间）用于即时P&L更新；`statusEvent`（任意状态变更）用于订单簿维护。生产系统需同时注册，确保不遗漏事件。

**部分成交决策逻辑**：
- **修改剩余量**（`modifyOrder`）：保留队列优先级，适合价格向有利方向移动时调整限价
- **取消重发**：重置队列位置，允许变更订单类型，适合需要重新定价或切换至市价的情景

#### 3.3.2 订单标识与核对

| 标识层级 | 字段 | 生成时机 | 用途 | 持久化 |
|:---|:---|:---|:---|:---|
| 本地标识 | `clientId` + `orderId` | 客户端 | 本地订单管理 | 会话级 |
| 交易所持久 | **`permId`** | 交易所接受后 | **盘后核对关键** | 永久 |

**盘后核对流程**：每日通过`reqExecutions`查询全部成交，以`permId`为键匹配本地日志，核对合约/方向/数量/价格/费用。差异项标记调查，可能原因包括网络丢包、交易所延迟报告、或极端行情下的快速成交聚合。

## 4. 投资组合与风险管理系统

### 4.1 统一持仓视图

#### 4.1.1 多品种仓位聚合

**股票与期货的计量差异**要求统一转换：

| 资产类型 | 原始单位 | 市值计算 | 多空表示 |
|:---|:---|:---|:---|
| 股票 | 股数 | `股数 × lastPrice` | 正负号（+多头，-空头）|
| 期货 | 合约数 | `合约数 × 乘数 × markPrice` | 显式分离（longContracts/shortContracts）|

**实时市值计算引擎**的刷新频率与策略匹配：中低频策略每秒或每Bar刷新，使用`last`（股票）和`markPrice`（期货，交易所官方结算价估计）。保守风控场景使用`bid`（多头）/`ask`（空头）计算最坏情况市值。

#### 4.1.2 保证金优化

**Portfolio Margin（组合保证金）**是本系统资金规模的关键优化点。相比Reg T的固定比例，Portfolio Margin基于风险模型计算，允许高度相关头寸的保证金抵扣：

| 场景 | Reg T保证金 | Portfolio Margin | 节省比例 |
|:---|:---|:---|:---|
| 股票多头$300K + ES空头对冲 | $150K + $11K = $161K | ~$50K（净敞口计费） | **~70%** |

**日内vs隔夜保证金动态监控**：
- **日内保证金**：ES约$500-1,000/手（25-50%隔夜要求）
- **隔夜保证金**：ES约$12,000-13,200/手
- **监控要点**：收盘前15-30分钟检查是否满足隔夜要求，不足时触发减仓或追加资金

### 4.2 实时风控指标体系

#### 4.2.1 账户层级监控

| 指标 | 定义 | 计算来源 | 预警阈值 | 熔断阈值 |
|:---|:---|:---|:---|:---|
| **Net Liquidation** | 账户净清算价值 | `NetLiquidation` | 日变动>±5% | 日变动>±10% |
| **Available Funds** | 可用资金（含杠杆）| `AvailableFunds` | <20%净值 | <10%净值 |
| **Excess Liquidity** | 超额流动性（最关键）| `ExcessLiquidity` | **<5%净值** | **<0（强制平仓）** |

**Excess Liquidity的实时监控**是防止强制平仓的最后防线。IBKR在Excess Liquidity为负时启动强制平仓，通常首先平掉亏损最大头寸。系统应在5%阈值时主动减仓，避免进入不可控的强制流程。

#### 4.2.2 仓位层级限制

| 限制类型 | 阈值 | 触发动作 | 设计原理 |
|:---|:---|:---|:---|
| 单票最大持仓 | 股票≤**10%**账户净值 | 禁止超阈值订单 | 分散化，避免单一黑天鹅 |
| 期货合约限制 | 单品种名义敞口≤**20-30%**净值 | 禁止超阈值订单 | 控制杠杆，防范跳空风险 |
| 组合Delta暴露 | \|净Delta\|≤**0.1-0.3** | 动态对冲调整 | Beta中性，控制系统性风险 |

### 4.3 自动风控动作

| 优先级 | 触发条件 | 风控动作 | 执行方式 | 恢复机制 |
|:---|:---|:---|:---|:---|
| **P0** | Excess Liquidity < **5%** | 禁止新开仓，启动减仓 | **自动执行** | 资金注入或持仓调整后 |
| **P0** | 当日PnL < **-2%** | 暂停交易，锁定仓位 | **自动执行** | 人工复盘后手动恢复 |
| **P0** | 当日PnL < **-5%** | 全部平仓，系统锁定 | **自动执行** | 全面调查后人工恢复 |
| P1 | 订单价格偏离市场价>**1%** | 订单拦截，记录告警 | 自动拦截 | 修正参数后重试 |
| P1 | 连续**5笔**订单异常拒绝 | 策略熔断，通知管理员 | 自动执行 | 故障排查后手动恢复 |
| P2 | API连接断开>**60秒** | 切换备用连接，告警 | 自动尝试 | 连接恢复后自动恢复 |

**日度亏损限制（-2%）**的设定基于账户净值，需考虑策略历史最大回撤和波动率特征。触发后系统进入"观察模式"——保留当前持仓但禁止新信号，等待人工审查或次日重置。

## 5. 策略研发与回测框架

### 5.1 策略类型体系

#### 5.1.1 股票策略

| 策略类型 | 核心逻辑 | 关键参数 | 适用市场 | 风险要点 |
|:---|:---|:---|:---|:---|
| **多因子选股** | 动量(12月收益)+质量(ROE稳定性)复合评分 | 因子权重、再平衡频率(月/季) | 趋势明确、分化市场 | 因子失效、风格切换 |
| **均值回归** | 价格偏离度Z-score，|Z|>2入场，|Z|<0.5出场 | 回望窗口(20日)、止损阈值(|Z|>3) | 震荡市场 | 趋势延续导致连续亏损 |
| **趋势跟踪** | 移动平均交叉或通道突破 | 短/长期均线(20/60日)、突破周期(20日) | 强趋势市场 | 震荡市假信号、滞后入场 |

#### 5.1.2 期货策略

| 策略类型 | 核心逻辑 | 关键参数 | 品种偏好 | 特殊考量 |
|:---|:---|:---|:---|:---|
| **CTA趋势** | 双均线交叉或唐奇安通道突破 | 均线周期、通道宽度、ATR止损 | ES/NQ/CL/GC | 参数稳健性、避免过度拟合 |
| **跨期套利** | 同一品种远近月价差收敛 | 价差历史分位数、持仓成本 | CL/GC(期限结构明显) | 换月成本、仓储物流因素 |

#### 5.1.3 混合策略

**股票多头 + ES做空对冲**是核心混合配置：

```
对冲合约数 = 股票组合市值 × 组合Beta / (ES价格 × 50)
```

**动态调整机制**：每日收盘后重新计算组合Beta，|ΔBeta|>0.1时调整对冲比率。设置对冲比率上下限（50%-150%理论值）避免过度交易。对冲成本包括：ES滚动成本（contango/backwardation结构）、保证金占用、以及基差风险（ES与股票组合的不完全相关）。

### 5.2 回测引擎设计

#### 5.2.1 事件驱动架构

**策略逻辑与实盘复用**是核心设计目标。事件处理器统一处理：
- `BarEvent`：新K线形成，触发信号计算
- `TickEvent`：新tick到达，用于高频触发或滑点模拟
- `OrderEvent`：订单状态变更
- `FillEvent`：成交确认，更新持仓和P&L

**滑点模型精细化**：

| 标的类型 | 滑点模型 | 参数说明 |
|:---|:---|:---|
| 股票 | **2bps + 0.5%×(订单量/日均成交量)** | 基础成本+市场冲击 |
| 期货（主力） | **1 tick + 0.2×(订单量/订单簿深度)** | 基础成本+深度衰减 |
| 期货（换月期） | **2-3 tick + 额外价差成本** | 流动性恶化调整 |

#### 5.2.2 期货特殊处理

**连续合约构建**：维护`contract_chain`表记录合约生命周期，`continuous_map`表记录每日主力合约标识。回测引擎根据交易日期自动切换数据源，换月成本（价差+双倍手续费）从P&L中扣除。

**保证金模拟**：日内头寸使用日内保证金率，收盘后切换至隔夜保证金率。可用资金不足隔夜要求时标记为保证金不足事件。

### 5.3 绩效分析与压力测试

#### 5.3.1 统一绩效指标

| 指标 | 计算公式 | 目标值 | 解读 |
|:---|:---|:---|:---|
| **CAGR** | (期末/期初)^(1/年数)-1 | >15% | 年化复合增长 |
| **Sharpe** | (收益-无风险利率)/波动率 | >1.0 | 风险调整后收益 |
| **Max Drawdown** | 峰值至谷底最大跌幅 | <20% | 极端损失体验 |
| **Calmar** | CAGR/Max Drawdown | >0.5 | 收益-回撤平衡 |
| **Win Rate** | 盈利交易/总交易 | 40-60% | 趋势策略通常<50% |

**分品种归因**：股票Alpha（选股超额收益）vs 期货Beta（市场暴露收益）分离，评估真实能力来源。

#### 5.3.2 压力测试场景

| 场景 | 时间窗口 | 核心特征 | 验证要点 |
|:---|:---|:---|:---|
| **2020疫情冲击** | 2020年2-4月 | VIX飙升至82，流动性枯竭，多次熔断 | 止损执行、极端波动下的订单状态 |
| **2022加息周期** | 2022年3-12月 | 持续熊市，股债双杀，波动率维持高位 | 趋势跟踪适应性、对冲效果 |
| **2018闪崩** | 2018年2月/10月/12月 | VIX单日翻倍，做空波动率策略崩溃 | 尾部风险管理、相关性突变 |

## 6. 生产部署与运维监控

### 6.1 部署架构

**同机部署的核心组件**：

| 组件 | 进程类型 | 资源需求 | 监控要点 |
|:---|:---|:---|:---|
| IB Gateway | Java应用 | 1GB内存，1核CPU | 内存泄漏、GC暂停 |
| 交易系统(Python) | Python 3.10+ | 2-4GB内存，2核CPU | CPU使用率、GIL竞争 |
| 数据存储(SQLite/InfluxDB) | 嵌入式/独立服务 | 视数据规模 | 磁盘I/O、查询延迟 |

**进程管理**：systemd服务配置`Restart=always`，`RestartSec=10`避免快速重启风暴。Supervisor作为跨平台替代，支持进程组管理和Web监控界面。

**配置分离原则**：敏感信息（账户凭证、API密钥）通过环境变量或HashiCorp Vault注入，代码仓库仅保留配置模板。

### 6.2 监控与告警

| 监控层级 | 具体指标 | 采集频率 | 告警阈值 |
|:---|:---|:---|:---|
| 基础设施 | CPU/内存/磁盘/网络 | 10秒 | 资源使用率>80% |
| API连接 | 连接状态、心跳延迟、消息速率 | 5秒 | 断开或延迟>500ms |
| 交易执行 | 订单状态、成交延迟、滑点统计 | 实时 | 订单拒绝、延迟>2s |
| 策略健康 | 信号生成频率、持仓一致性 | 每分钟 | 信号缺失、持仓偏差 |
| 风险指标 | Excess Liquidity、PnL | 实时 | 触及风控线 |

**告警渠道分级**：P0（短信+电话+企业微信）、P1（邮件+企业微信）、P2（仅日志）。

### 6.3 灾难恢复

| 恢复层级 | 机制 | 目标RTO | 实现要点 |
|:---|:---|:---|:---|
| 状态持久化 | 每30秒快照：持仓、订单、策略状态 | — | SQLite/Redis本地+远程双副本 |
| 快速回滚 | 从最近一致状态恢复 | **<5分钟** | 自动化部署脚本、数据库快照恢复 |
| 手动接管 | 极端情况人工干预 | 视情况 | TWS GUI备用、电话交易流程、持仓核对清单 |

**定期演练**：每季度模拟故障场景（API断开、服务器崩溃、网络分区），验证恢复流程有效性并更新Runbook。
